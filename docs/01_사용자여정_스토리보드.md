# FeedbackAnalyzer `src` — 사용자 여정 스토리보드

**Persona**: C++17·클린 아키텍처 학습자 (중급, TDD/리팩토링 실습)  
**학습 목표 (명시)**: 감정 분류 **알고리즘 정확도**가 아니라 **계약(schema·error.code)·Catch2 테스트·Boundary/Control/Entity 레이어 분리·회귀 보호**를 설계·증명하는 것.  
**범위**: `src` 학습 시스템 · **코드·구현 없음**

---

## 스토리보드 한눈에 보기

```
[Awareness]  →  [Entry]  →  [Action]  →  [Validation]  →  [Outcome]
  불일치 발견     계약·규칙     RED→GREEN      커버리지·Matrix   리뷰·증명
  Invariant      Gherkin       Dual-Track     골든·SC-01~07    “맞다”는 증거
```

---

## Stage 1 — Awareness (문제 인식)

> **프레임**: “왜 숫자가 다르지?” → **불변식(Invariant) 언어**로 재정의

| 차원 | 내용 |
|------|------|
| **Action** | 로컬 서버를 띄우고 동일 피드백으로 분석·필터·CSV를 순서대로 실행하며, 감정 비율·건수·목록을 스크린샷·메모로 비교한다. |
| **Action** | `TextAnalyzer` 집계 경로와 `Filters` 필터 경로가 **서로 다른 키워드·우선순위**를 쓰는 지점을 표시한다. |
| **Thinking** | “키워드 if-else를 더 넣으면 되겠지”가 아니라, **어느 경로가 진실인지 계약이 없다**는 결론에 도달한다. |
| **Thinking** | ML·고급 NLP가 아니라 **규칙이 둘이면 결과가 둘**이라는 구조 문제로 본다. |
| **Emotion** | 혼란(“버그인가 요구사항인가”) → 짧은 안도(“재현 가능한 학습 이슈다”). |
| **Pain** | 같은 문장인데 대시보드·필터·다운로드가 달라 **데이터를 신뢰할 수 없다**. |
| **Pain** | 실패가 빈 화면·경고 한 줄로만 보여 **RED 테스트를 쓸 거리**가 없다. |
| **Opportunity** | 불일치를 **INV-D1·D6** 같은 이름으로 고정하면, 이후 Story·Gherkin·Catch2가 같은 언어를 쓴다. |
| **Opportunity** | “알고리즘 튜닝” 대신 **단일 Registry·Converter** 목표가 팀·강사와 공유 가능해진다. |

**학습 포인트 (이 Stage)**: 문제 = 분류 정확도 경쟁이 아니라 **계약 부재·이중 규칙**.

---

## Stage 2 — Entry (진입·계약 정의)

> **프레임**: 요구사항 패키지·Gherkin·`.cursorrules`로 **행위를 문서화**

| 차원 | 내용 |
|------|------|
| **Action** | Level 1 Epic 성공 기준(SC-01~07)과 ST-01~06 Acceptance Criteria를 읽고, 체크 가능한 bullet만 남긴다. |
| **Action** | Input/Output/Error schema와 허용 감정·카테고리 enum, Hub·우선순위 표를 **한 페이지 계약**으로 작성한다. |
| **Action** | `src/features` Gherkin(GH-01~13)과 Invariant 태그를 열어 **시나리오 = 곧 테스트 명세**임을 확인한다. |
| **Thinking** | “기능 목록”이 아니라 **실패 시 `error.code`·`field`** 가 먼저 정의되어야 구현 순서가 정해진다. |
| **Thinking** | Boundary / Control / Entity 역할을 그려 **어디에 if-else가 있으면 안 되는지** 경계를 정한다. |
| **Emotion** | 막막함(문서가 많음) → 집중(체크리스트에 답이 있다). |
| **Pain** | 계약 없이 코딩하면 **리팩터가 의미 변경인지 구조 변경인지** 구분이 안 된다. |
| **Pain** | 팀마다 “중립” 정의가 달라 **논쟁이 테스트로 끝나지 않는다**. |
| **Opportunity** | `EMPTY_TEXT`, `UNKNOWN_EMOTION` 등 **기계 검증 가능한 실패**로 RED 작성이 시작된다. |
| **Opportunity** | Dual-Track 전제로 **Domain 테스트는 HTTP 없이** 돌릴 수 있음이 명확해진다. |

**학습 포인트 (이 Stage)**: 진입 = IDE 열기가 아니라 **계약·Gherkin·레이어 규칙 동의**.

---

## Stage 3 — Action (실행·Dual-Track TDD)

> **프레임**: RED → GREEN → (아직 REFACTOR 보류) — **테스트가 설계를 이끈다**

| 차원 | 내용 |
|------|------|
| **Action** | Domain: Catch2 RED — `classify`/`aggregate`/`filter` 불일치·Hub·우선순위 골든부터 추가한다. |
| **Action** | GREEN: `UnitRegistry` + `Converter` 최소 구현으로 **이중 SENTIMENT 제거**, 한 경로만 통과시킨다. |
| **Action** | Boundary: Fake Registry로 Validator·ErrorMapper·Presenter(JSON/CSV/HTML) **계약만** RED→GREEN한다. |
| **Action** | Control: Analyze / Upload / Filter / Export 유스케이스가 Entity를 호출만 하게 연결한다. |
| **Thinking** | “테스트가 귀찮다”가 아니라 **테스트가 레이어 위반을 즉시 적발**한다고 받아들인다. |
| **Thinking** | 키워드 추가는 코드 분기가 아니라 **`registerUnit`·loadRatios** 로 가야 OCP 학습이 성립한다. |
| **Emotion** | RED 실패의 쾌감(“재현됐다”) → GREEN 후 안정감 → REFACTOR 욕구(“이제 정리해도 된다”). |
| **Pain** | main·전역 상태·cout에 섞여 **Domain 테스트가 느리고 불안정**해진다. |
| **Pain** | GREEN에서 테스트 기대값을 낮추면 **학습 증거가 사라진다**. |
| **Opportunity** | Fake/Mock Boundary로 **HTTP 없이** 사이클 시간을 줄인다. |
| **Opportunity** | Presenter 추가만으로 JSON/CSV/표 확장 — **분류 로직 무변경** OCP 체험. |

**학습 포인트 (이 Stage)**: 행동 = 코딩량이 아니라 **RED-GREEN 사이클·레이어별 테스트**.

---

## Stage 4 — Validation (검증·회귀 보호)

> **프레임**: “돌아가네”가 아니라 **측정·매핑·골든**으로 증명

| 차원 | 내용 |
|------|------|
| **Action** | Catch2 전 태그 `[domain]` `[boundary]` `[data]` GREEN 확인; Domain line ≥95%, branch ≥90% 측정한다. |
| **Action** | 골든 피드백 N≥20으로 `classify` = `aggregate` 단건 = `filter` 판별 **IT 불일치 0건**을 기록한다. |
| **Action** | Gherkin GH-01~13 ↔ Catch2 테스트 ID **Traceability Matrix** 빈칸 0을 점검한다. |
| **Action** | REFACTOR: 전체 GREEN 후 main 분리·전역 제거·금지 패턴(이중 Rule, cout 디버그) 스캔한다. |
| **Thinking** | 커버리지 숫자는 **목적이 아니라 계약 누락 탐지 보조**라고 본다. |
| **Thinking** | `error.code` 변경은 **의도적 버전·테스트 동반** 없으면 실패로 간주한다. |
| **Emotion** | 검증 중 긴장(감점·회귀) → Matrix 채움 후 자신감(“설명 가능”). |
| **Pain** | 리팩터 후 숫자만 바뀌면 **왜 맞는지 말로만 방어**하게 된다. |
| **Pain** | Gherkin과 테스트가 어긋나면 **요구사항 드리프트**가 팀 전체로 퍼진다. |
| **Opportunity** | SC-01~07을 **완료 증거 체크리스트**로 제출·리뷰할 수 있다. |
| **Opportunity** | Invariant 태그로 회귀 시 **어느 계약이 깨졌는지** 바로 좁힌다. |

**학습 포인트 (이 Stage)**: 검증 = 수동 클릭이 아니라 **커버리지·골든·Matrix·금지 패턴 0건**.

---

## Stage 5 — Outcome (결과·학습 완료)

> **프레임**: 제품 출시가 아니라 **증명 가능한 파이프라인** 인도

| 차원 | 내용 |
|------|------|
| **Action** | 팀 리뷰에서 “알고리즘 설명” 대신 **계약 표·GH 시연·커버리지·불일치 0건**을 보여준다. |
| **Action** | 동적 감정 등록·YAML 로드·JSON/CSV 출력 중 **Converter 분기 추가 없이** 확장한 사례 1개를 시연한다. |
| **Action** | 레거시 대비 Before/After: 이중 Rule 제거, 전역 상태 제거, 단일 Registry 다이어그램을 공유한다. |
| **Thinking** | 이 프로젝트의 산출물은 실행 파일이 아니라 **테스트·계약·레이어가 남는 습관**이다. |
| **Thinking** | 다음 기능(Trend·DB)도 **Entity 계약 먼저** 확장할 수 있겠다고 연결한다. |
| **Emotion** | 성취(“맞다고 증명했다”) · 여운(“알고리즘보다 설계가 먼저”). |
| **Pain** | 구조만 예쁘고 골든이 없으면 **실무에서 다시 불신**을 당할 것이라는 걸 안다. |
| **Opportunity** | 포트폴리오·코드 리뷰에서 **Invariant·error.code·Dual-Track** 언어로 소통 가능. |
| **Opportunity** | 동일 패턴을 다른 도메인(단위 변환·요금 계산)에 **계약-first**로 재사용. |

**학습 포인트 (이 Stage)**: 성과 = UI 완성도가 아니라 **SC 충족 + 설명 가능한 회귀 보호**.

## Stage × 학습 목표 매핑

| Stage | 계약 | 테스트 | 레이어 분리 |
|-------|------|--------|-------------|
| Awareness | 불일치를 Invariant로 이름 붙임 | RED가 필요함을 인식 | 이중 Rule = 레이어 붕괴 |
| Entry | schema·error.code·Gherkin | GH = 명세 | B/C/E 역할 합의 |
| Action | Validator·Presenter 계약 구현 | RED→GREEN·Fake | Entity 순수·Control 조율 |
| Validation | code 동결·Matrix | 커버리지·골든·IT | REFACTOR·금지 패턴 |
| Outcome | 리뷰 언어 = 계약 | 증거 제출 | OCP 확장 시연 |
